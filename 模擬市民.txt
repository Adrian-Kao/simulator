⑤ Policy Schema
所有政策最後一定要轉成 machine-readable。
例如：
公館商圈新增 500 個停車位。
不能只是一句文字。
要變：
{
 "policyType": "parking_capacity",
 "location": "zone_A",
 "capacityChange": 500,
 "parkingFee": 50,
 "openingHours": {
   "start": "08:00",
   "end": "23:00"
 },
 "effectiveDate": null
}
這個地方就是 Gemini API 第一個主要用途。
Gemini 的 Structured Outputs 能限制模型輸出符合指定 JSON Schema；Function Calling 則可以讓模型透過定義好的 functions/tools 與程式系統互動，非常適合這種「政策文字 → 結構化政策 → 執行工具」架構。
________________

⑩ Gemini Diagnosis Agent
這是 Gemini 最關鍵的角色之一。
假設：
Policy V1


新增 500 個停車位
模擬：
找停車時間      -48% ✓
商圈人流        +9% ✓


但：


進入汽車        +22% ✕
住宅區車流      +16% ✕
平均旅行時間    +13% ✕
CO₂             +11% ✕
系統先整理成：
Diagnostic Dataset
Gemini Diagnosis Agent 分析：
為什麼沒有達標？
哪個 KPI 是主要瓶頸？
有哪些 second-order effects？
哪個 Agent group 改變行為？
哪個區域出現異常？
哪個時段最嚴重？
這裡很適合 Gemini 的 reasoning 能力。

⑫ Agent Framework
既然你們確定要使用 Agent，我會建議評估：
Google Agent Development Kit（ADK）
它是 Google 官方提供的 Agent 開發框架，定位就是建立、管理、測試、評估與部署 Agent，也支援 multi-agent 與 tool integrations。
但我會限定它的用途：
Google ADK


├── Policy Diagnosis Agent
├── Policy Planner Agent
├── Experiment Agent
└── Future Multi-Agent Orchestration
不要：
Google ADK
↓
控制全部 50,000 個居民 Agent
Simulation Population 還是自己做。

Agent simulation 一定要有：

例如：
seed = 48219
確保：
